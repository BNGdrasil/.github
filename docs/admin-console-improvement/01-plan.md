# 어드민 콘솔 개선 계획

확정일: **2026-09-20 KST**. 이 문서는 그날 정리한 판단과 계획을 그대로 옮긴 것이며, 이후 진행 상황은 [02 현황 점검](02-status-2026-09-22.md)에 따로 기록한다.

## 1. 배경과 역할 정의

Bantheon의 관리자 콘솔은 2026년 9월 전면 보수를 거치면서 화면에 들어가 있던 가짜 데이터를 모두 제거했다. 임의로 채워 넣던 uptime과 요청량과 자원 사용률을 지웠고, 게이트웨이가 계산할 수 없는 값은 `null`로 내려받아 "미수집"이라고 표시하도록 바꿨다. 그 결과 콘솔은 실제로 동작하는 얇은 화면이 되었다.

문제는 얇아진 다음이다. 로그와 메트릭의 조회는 이미 Grafana가 담당하고 있고, 그 뒤에는 Prometheus와 Loki가 있다. 관리자 콘솔이 같은 일을 다시 하면 기능이 중복될 뿐이며, 운영 개선 03 문서도 관리자용 별도 로그 검색 시스템을 만들지 않고 Grafana Explore를 대안으로 삼는다고 이미 결정해 두었다. 그래서 콘솔에 남는 고유한 역할은 두 가지로 좁혀진다.

1. **조작**: Prometheus는 상태를 관찰할 뿐이고 서비스 등록부를 바꾸거나 계정을 정지하는 일을 대신하지 못한다. 상태를 바꾸는 행위는 콘솔이 맡아야 한다.
2. **여러 시스템을 묶은 운영 판단**: 백업이 언제 성공했는지, 지금 어떤 경보가 발화 중인지, 현재 배포된 빌드가 무엇인지를 한 화면에서 함께 보여 주는 일은 개별 대시보드가 대신하기 어렵다.

이 두 가지 역할이 지금 비어 있기 때문에 콘솔의 의의가 약해 보였다. 아래 계획은 비어 있는 두 역할을 채우는 순서를 정한 것이다.

## 2. 설계 원칙

- 기술 구성은 React와 Vite와 React Query와 일반 CSS를 그대로 유지한다. UI 라이브러리와 차트 라이브러리는 도입하지 않는다.
- Grafana를 포크하지 않고, 자체 로그 검색 기능을 만들지 않으며, 브라우저가 임의의 PromQL을 던질 수 있는 프록시 엔드포인트도 만들지 않는다. 서버가 미리 정해 둔 질의만 수행하는 고정 질의 엔드포인트만 허용한다.
- 데이터 계약은 운영 개선 08 문서의 기준을 유지한다. 실패를 `0`으로 위장하지 않으며, 수집하지 않은 값은 `null`로 내리고, 요청이 실패하면 error로 구분하며, 이전 값만 남아 있으면 stale로 표시한다.
- 서버 기능을 먼저 배포하고 그 다음에 화면을 연결한다. 화면이 아직 없는 서버 엔드포인트는 허용하지만, 서버가 없는 화면은 만들지 않는다.
- 삭제처럼 되돌리기 어려운 조작에는 확인 다이얼로그를 붙이고, 대상과 영향을 먼저 보여 준다.

## 3. 범위에서 제외한 항목

| 제외 항목 | 이유 |
|---|---|
| 감사 로그 | 운영자가 한 명이고, 다른 메인테이너 계정을 추가할 계획이 없다. 누가 무엇을 했는지 구분할 필요가 생기지 않는다 |
| 다중 운영자를 전제한 기능 | 승인 흐름처럼 두 사람 이상을 가정하는 기능은 같은 이유로 만들지 않는다 |
| Bsgard VPC 관리 화면 | 연결할 백엔드가 아직 없다. 백엔드가 생긴 다음에 다시 판단한다 |

감사 로그를 제외한 결정은 운영자 수가 늘어나면 뒤집는다. 그때에는 Bifrost의 `GET /admin/api/logs/audit`가 501을 반환하고 있다는 점부터 다시 검토한다.

## 4. 단계별 계획

### P1: Bantheon만으로 완료할 수 있는 작업

서버에 이미 있는 기능을 화면에 연결하는 단계다. Bifrost를 고치지 않아도 끝낼 수 있다.

| 항목 | 필요한 서버 변경 | 화면 | 완료 기준 |
|---|---|---|---|
| P1-a 서비스 상세와 수정과 삭제, 단건 헬스 확인 | 없음 | 서비스 목록의 각 행에서 상세로 들어가고, 상세에서 수정과 삭제와 헬스 확인을 수행한다 | 저장한 다음 서버에서 다시 조회한 값이 화면과 일치하고, 삭제에 확인 다이얼로그가 붙는다 |
| P1-b 개요 화면의 게이트웨이 준비 상태 | 없음 | 운영 개요에 Bifrost `/ready`의 `database`와 `registry`와 `service_count`를 표시한다 | 503 응답일 때 오류 문자열을 그대로 보여 주고, 정상일 때와 구분된다 |
| P1-c Grafana 연결 정합성 정리 | 없음 | 관측 화면이 만드는 Grafana 링크의 질의와 대상 대시보드를 바로잡는다 | 링크로 이동했을 때 실제로 해당 서비스의 로그와 대시보드가 열린다 |

P1-a에는 먼저 확인해야 할 사항이 하나 있다. Bifrost의 `GET /admin/api/services/{id}/health`는 관리자 API 문서에 "해당 서비스에 실제로 health check를 수행합니다"라고 적혀 있지만, 실제 구현은 데이터베이스에 저장된 마지막 상태를 돌려준다. 단건 실시간 probe가 필요하다면 Bifrost에 probe를 수행하는 엔드포인트를 새로 추가해야 하고, 그럴 생각이 없다면 문서를 실제 동작에 맞게 고쳐야 한다. 둘 중 하나를 정하기 전에는 화면에 "지금 확인"이라는 표현을 쓰지 않는다.

P1-c는 코드를 읽다가 추가로 발견한 정합성 문제 두 가지를 묶은 것이다.

- 관측 화면이 만드는 Loki 질의는 `{service="<Bifrost에 등록된 서비스 이름>"}` 형태인데, Loki가 실제로 붙이는 `service` 라벨의 값은 Docker Compose의 서비스 이름이다. 두 값의 도메인이 달라서 링크를 눌러도 결과가 비어 나올 수 있다. 라벨 값을 변환하는 표를 두거나 Loki 쪽 라벨 부여 규칙을 맞추는 방식 가운데 하나를 골라야 한다.
- Baedalus에 Grafana 대시보드 여덟 종이 uid와 함께 배포되어 있는데(`bngdrasil-overview` 등), 관리자 콘솔은 이 uid를 직접 링크하지 않는다. 운영자가 Grafana 안에서 대시보드를 다시 찾아야 하므로 진입 링크를 붙인다.

### P2: Bifrost의 서버 변경이 먼저 필요한 작업

콘솔이 "여러 시스템을 묶은 운영 판단"을 맡는다는 역할 정의를 실제로 채우는 단계다. 두 항목 모두 Bifrost가 Prometheus 계열 구성 요소에 고정 질의를 던지고 그 결과만 화면에 내려 주는 구조를 사용한다.

| 항목 | 필요한 서버 변경 | 화면 | 완료 기준 |
|---|---|---|---|
| P2-a 백업 현황 | Bifrost에 읽기 전용 엔드포인트를 추가한다. Prometheus에 `bngdrasil_backup_*` 지표를 고정 질의로 조회해서 마지막 성공 시각과 오프사이트 전송 시각과 검증 시각과 각각의 결과를 돌려준다 | 운영 개요와 운영 설정에 마지막 백업 결과를 표시한다 | 실제 백업을 한 번 돌린 뒤 화면의 시각이 갱신되고, 지표를 읽지 못하면 `null`과 unavailable로 표시된다 |
| P2-b 발화 중 알림 요약 | Bifrost에 Alertmanager 또는 Prometheus `/api/v1/alerts`를 고정 질의로 조회하는 엔드포인트를 추가한다 | 운영 개요에 발화 중 알림 개수와 Grafana로 가는 링크를 표시한다 | 시험 경보를 발화시켰을 때 개수가 늘고, 해소되면 줄어든다 |

두 엔드포인트 모두 브라우저에 Prometheus나 Alertmanager의 접속 정보를 내려보내지 않는다. 질의 문자열은 서버 코드에 고정하며 요청 본문으로 받지 않는다. 백업 상태의 stale 판정에는 화면 공통의 90초 기준을 쓰지 않고 백업 주기를 기준으로 삼는다.

### P3: 이후 단계

| 항목 | 필요한 서버 변경 | 화면 | 완료 기준 |
|---|---|---|---|
| P3-a 릴리스와 배포 현황 | Bifrost와 Bidar가 빌드 SHA와 빌드 시각을 노출하도록 이미지를 빌드할 때 값을 주입한다. VM1의 정적 릴리스가 남기는 `releases/<sha>`와 `current`와 `previous` 정보를 읽는 방법을 함께 검토한다 | 운영 설정에 현재 배포된 빌드와 되돌릴 수 있는 이전 지점을 표시한다 | 배포를 한 번 수행한 뒤 화면의 SHA가 실제 배포 SHA와 일치한다 |
| P3-b API 키 관리 | Bidar에 `api_keys` 모델만 있고 CRUD와 라우트가 없다. Bidar에 라우트를 먼저 만들고, Bifrost가 프록시하도록 추가한 다음, 콘솔 화면을 붙인다 | 사용자 화면 옆에 API 키 목록과 발급과 폐기 화면을 추가한다 | 발급한 키로 실제 인증이 되고, 폐기한 키가 거절된다 |
| P3-c 위생 작업 | 없음 | `DashboardPage`에 하드코딩된 `INFRA_HISTORY` 목록을 제거한다 | admin에 eslint 설정 파일이 생기고 CI에 lint 단계가 추가되며, Playwright 스모크 테스트가 저장소에 커밋되어 실행된다 |

P3-b는 순서를 지켜야 한다. Bidar 라우트를 먼저 만들고, 그 다음에 Bifrost 프록시를 추가하고, 마지막에 콘솔 화면을 붙인다. 서버 기능을 먼저 배포한다는 원칙이 여기에 그대로 적용된다.

## 5. 어드민 밖에서 처리할 후속 과제

코드를 확인하는 과정에서 관리자 콘솔의 범위를 벗어나는 결함을 두 건 발견했다. P2에서 Bifrost를 고칠 때 같은 작업으로 함께 처리한다.

- Bifrost의 `SERVICE_URL_ALLOWED_HOSTS`와 `SERVICE_URL_DENIED_HOSTS`는 환경 변수 값이 빈 문자열이면 목적지 정책 검사가 조용히 꺼진다. 설정을 잘못 적었을 때 경고 없이 보호 장치가 사라지므로, 빈 값과 설정하지 않은 상태를 구분해서 처리해야 한다.
- `BACKEND_CORS_ORIGINS`를 쉼표로 구분해 파싱할 때 빈 origin이 목록에 들어갈 수 있다. 빈 항목을 걸러내야 한다.
